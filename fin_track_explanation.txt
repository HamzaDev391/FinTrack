# FinTrack — Project Context

## 1. Project Identity

**Project:** FinTrack

**Type:** Flutter mobile application

**Purpose:** Portfolio project demonstrating professional Flutter development.

FinTrack is a **personal finance management application** designed to demonstrate:

* Flutter development
* Dart
* State management
* Local database persistence
* SQLite
* Drift
* Repository architecture
* CRUD operations
* Data modeling
* Search and filtering
* Sorting
* Financial calculations
* Data visualization
* Navigation
* Form validation
* Error/loading/empty states
* Material 3 UI
* Local preferences
* Maintainable feature-oriented architecture

FinTrack is a **portfolio application**, not a production fintech platform.

# 5. Architecture

The main application data flow is:

```text
Flutter UI
    ↓
Riverpod
    ↓
Repository
    ↓
Drift
    ↓
SQLite
```

The UI should not directly communicate with the database.

Repositories encapsulate database operations.

Riverpod manages application state and exposes data to presentation layers.

Drift handles structured local persistence.

Simple application preferences such as theme and currency do not require database tables.

# 7. Database Design

## Categories

```text
categories
──────────
id
name
type
icon
isDefault
```

Category types:

```text
income
expense
```

---

## Transactions

```text
transactions
────────────
id
title
amount
type
categoryId
date
note
createdAt
```

Transaction types:

```text
income
expense
```

Relationship:

```text
Category
    │
    └────── * Transactions
```

One category can contain many transactions.

---

## Budgets

```text
budgets
───────
id
categoryId
amount
month
year
createdAt
```

Relationship:

```text
Category
    │
    └────── * Budgets
```

A category can have multiple budgets across different months.

However, there can only be **one budget for a category in a particular month/year**.

Database constraint:

```text
UNIQUE(categoryId, month, year)
```

---

# 8. Money

Financial amounts are represented using integer values rather than floating-point values to avoid unnecessary floating-point precision problems.

Do not casually change financial storage to `double`.

The stored value should be formatted for display according to the selected currency preference.

# 11. Categories Feature

Users can:

* View categories
* Create custom categories
* Edit categories
* Delete categories

Category deletion must account for existing transaction relationships.

A category currently referenced by transactions should not simply be deleted.

The intended V1 behavior is:

```text
Prevent deletion
+
Tell the user how many transactions use the category
```

Default categories should also be handled appropriately so the application's seeded data remains safe.

---

# 12. Budgets Feature

Budgets are monthly budgets associated with expense categories.

A budget contains:

```text
id
categoryId
amount
month
year
createdAt
```

Users can:

* Create budget
* Select expense category
* Set amount
* Select month
* Edit budget
* Delete budget
* View spending against budget
* View remaining budget
* View percentage used

Example:

```text
Food
Budget: Rs. 10,000

Spent: Rs. 7,500
Remaining: Rs. 2,500

75%
```

Budget spending is calculated from the relevant expense transactions for that category and month.

# 19. Local-First Behavior

FinTrack does not require an internet connection.

The intended persistence flow is:

```text
User opens application
        ↓
Read SQLite database
        ↓
Drift
        ↓
Repository
        ↓
Riverpod
        ↓
UI
```

For a write operation:

```text
User input
    ↓
Validation
    ↓
Application state
    ↓
Repository
    ↓
Drift
    ↓
SQLite
    ↓
Updated state
    ↓
UI
```
